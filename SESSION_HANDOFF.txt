KNOWN GAME API FACTS (hard-won from decompilation)
--------------------------------------------------------------------------------
- unusedCount on ItemInfo is uint — must cast to int explicitly
- HotkeyManager is both a namespace AND a class name:
    use global::HotkeyManager.HotkeyManager and global::HotkeyManager.KeyCombo
- UIWindowManager methods: CloseMostRecentMenu(), CloseAllMenus(), ToggleReportWindow()
    NO: CloseTopWindow, IsAnyWindowOpen, Update
- UIModalWindowManager fields: modalWindowPrefab, modalWindowCustomContentSlot, customContent
    NO: modalWindowInstance, Update method
- UIManager fields: _windowManager, _modalWindowManager
    NO: building info window reference of any kind
- UIBuildingInfoWindow: found via Object.FindObjectsOfType<UIBuildingInfoWindow>(true)
- InputManager.selectedObject = currently selected GameObject (public field)
- Building.UpgradeBuilding() is the upgrade method (NO CanUpgrade/Upgrade pair)
- ItemSetupData.ItemEntry uses .name field (NOT .displayName)
- Input state machine: InputManager.inputStateMachine (StateMachine component)
    States: Input_Default, Input_SelectGameObject, Input_ModalWindow,
            Input_PlaceBuilding, Input_TechTree, Input_OptionsMenu, etc.
- StateMachine.currentState = private field with current active state
    NOTE: state machine MAY use a stack — currentState may not reflect pushed states
    like Input_ModalWindow if it's pushed on top. This is why IsInModalState()
    was unreliable and we switched to IsModalVisible() UI check instead.
- Modal buttons: found by searching active UIModalWindowManager children for
    GameObjects with 2+ Button components, then searching by name for
    confirm/yes/ok vs cancel/no/close keywords

ARCHITECTURE: HOW HOTKEY DISPATCH WORKS
--------------------------------------------------------------------------------
Unity runs our OnUpdate() every frame. The game runs its own Update() chain.
Both see the same Input.GetKeyDown() state — there's no "consuming" a key press.

Our approach:
1. OnUpdate() runs first in our mod.
2. We compute FrameModalVisible and FrameBuildingWindowActive (UI state checks).
3. If modal visible: we handle Y/N by clicking the modal button, then return early
   so none of our OTHER handlers run. But the game still processes Y/N.
4. HotkeySuppressPatch prefix on HotkeyManager.GetKeyComboDown returns false
   when either context flag is set — this stops the GAME from processing hotkeys
   in those contexts (they route through HotkeyManager, not raw Input).
5. If building window active: our handlers fire via direct Input.GetKeyDown().
   Game's hotkeys for the same keys are suppressed via HotkeySuppressPatch.

Why not use the state machine (InputStateHelper)?
  InputManager.inputStateMachine.currentState reflection was tried but proved
  unreliable — IsInModalState() and IsSelectingGameObject() returned false even
  when those contexts were active. Likely a stack vs. single-state issue.
  InputStateHelper.cs still exists but is no longer used in the main dispatch.
  Could be investigated further but direct UI checks are working well enough.
